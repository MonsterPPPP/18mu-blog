## Context

The repository contains only its initial commit. The content and technical decisions supplied outside the repository establish Markdown as the content source, Astro as the site framework, and Cloudflare Workers Static Assets as the deployment target. See proposal.md for motivation and the change specs for observable behavior.

## Goals / Non-Goals

**Goals:**

- Establish a working, deployable Astro site with the complete top-level information architecture.
- Make authoring, validation, committing, and release steps reproducible from repository documentation.
- Deploy a usable public draft without waiting for an embedding provider configuration.

**Non-Goals:**

- Implement semantic embeddings, vector storage, cognitive-map clustering, or random-walk traversal before the externally selected provider is configured.
- Build authentication, comments, CMS editing, analytics, a database, or custom-domain routing.
- Treat sample content as final personal biography, experience, or portfolio material.

## Decisions

### Astro static site with small client islands

Use Astro Content Collections for source validation and static routes. Use a small React island only for blog search; map and walk pages remain honest static states until semantic data exists. This preserves static performance and leaves a clear extension point. A full React/Next application is rejected because it adds server and content-management complexity not required by the Markdown workflow.

### Repository-local content source and guidance

Move the agreed architecture documents into `docs/` and add `AGENTS.md`, `CONTRIBUTING.md`, and content templates. Content collections define the executable schema while docs explain author intent. This keeps the operational contract versioned beside the code. External desktop notes cannot be relied on by a future clone or Agent.

### Worker Static Assets deployment

Use Wrangler with an `assets` directory generated by Astro. A minimal Worker entry delegates normal requests to static assets and reserves `/api/` for future protected semantic synchronization. This uses one deployable unit and avoids creating Pages plus a separate Worker. KV and provider secrets are intentionally absent until semantic synchronization is implemented.

### Deployment automation

Use a local `npm run deploy` command for first publication and a GitHub Actions workflow for subsequent `main` releases. The workflow requires `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` secrets; local OAuth proves the account path now but is never copied to GitHub.

### Minimum content and visual system

Ship concise, clearly marked draft content that exercises every route. The visual system uses a compact editorial layout, warm paper and ink colors with green/blue accents, responsive navigation, and no generic theme dependency. The initial draft demonstrates information hierarchy without claiming final personal content.

## Risks / Trade-offs

- [No embedding provider is configured] -> Map and walk expose documented pending states, not fake relationship data; add Worker/KV synchronization only after provider selection.
- [GitHub Actions cannot use local Wrangler OAuth] -> Document exact repository secrets and validate local deployment before relying on CI.
- [Workers Static Assets configuration differs across Wrangler versions] -> Pin compatible Wrangler version and verify with a real production deployment plus HTTP requests.
- [Sample data can be mistaken for final information] -> Label draft content and make replacement paths obvious in contributor guidance.

## Migration Plan

1. Create the project, content collections, workflow, and deployment configuration.
2. Run lint/build checks locally and deploy through authenticated Wrangler.
3. Verify the workers.dev production URL and primary routes.
4. Commit the complete baseline with a Conventional Commit and push to `main`.
5. Add GitHub Cloudflare secrets to activate automated releases; until then, the workflow is intentionally present but cannot authenticate.

Rollback is `wrangler rollback` to a prior Worker deployment or redeploying a previously tagged Git commit. The initial deployment introduces no persistent data migration.
